# ТЗ: полноценные блюда и мобильный редактор рецептов

Дата: 2026-06-23  
Проект: `calories-tracker`

## Цель

Добавить в приложение полноценную сущность **"Блюдо / Рецепт"**, которую пользователь может создать вручную или собрать из уже существующих продуктов. После создания блюдо должно добавляться в дневник питания так же просто, как обычный продукт.

Ключевая идея: пользователь готовит, например, "Омлет с сыром", вводит общий вес блюда, КБЖУ или ингредиенты, прикрепляет фото, сохраняет блюдо, а потом добавляет в дневник 150 г этого блюда.

## Продуктовая логика

### Что такое блюдо

Блюдо должно быть пользовательской сущностью, связанной с текущим пользователем.

Блюдо может быть:

- ручным: пользователь сам вводит КБЖУ на 100 г;
- составным: пользователь добавляет ингредиенты из существующей базы продуктов;
- смешанным: пользователь добавляет ингредиенты, но может вручную скорректировать итоговые КБЖУ.

### Главные сценарии

1. Пользователь открывает раздел "Блюда" или "Рецепты".
2. Нажимает "Создать блюдо".
3. Вводит название, фото, описание, категорию/тип приема пищи.
4. Выбирает способ расчета:
   - вручную КБЖУ на 100 г;
   - из ингредиентов;
   - из ингредиентов с ручной коррекцией.
5. Если выбраны ингредиенты, добавляет продукты из текущей базы и граммовки.
6. Указывает итоговый вес готового блюда.
7. Приложение считает КБЖУ на 100 г.
8. Пользователь сохраняет блюдо.
9. Блюдо появляется в поиске при добавлении записи в дневник.
10. Пользователь выбирает блюдо, вводит граммы порции и добавляет в дневник.

## Интеграция с текущей базой

Сейчас в проекте есть:

- `Product` в `apps/api/src/products/schemas/product.schema.ts`;
- `Entry` в `apps/api/src/entries/schemas/entry.schema.ts`;
- `MealTemplate` в `apps/api/src/templates/schemas/meal-template.schema.ts`.

Нужно не ломать текущую модель дневника.

Рекомендуемый подход:

1. Добавить отдельную backend-сущность `Recipe` или `Dish`.
2. При сохранении блюда создавать или синхронизировать системный `Product` с `source: 'RECIPE'`.
3. В `Entry` можно продолжать использовать `productId`, потому что блюдо будет доступно как продукт.
4. В `ProductSource` добавить `RECIPE`.
5. В поиске продуктов показывать обычные продукты и блюда, но визуально помечать блюда бейджем "Блюдо".

Важно: не смешивать `MealTemplate` и `Recipe`.

- `MealTemplate` - это быстрый шаблон приема пищи из нескольких записей.
- `Recipe/Dish` - это одно блюдо с расчетом КБЖУ на 100 г.

## Backend

### Новая схема `Recipe`

Создать модуль:

- `apps/api/src/recipes/recipes.module.ts`
- `apps/api/src/recipes/recipes.controller.ts`
- `apps/api/src/recipes/recipes.service.ts`
- `apps/api/src/recipes/schemas/recipe.schema.ts`
- `apps/api/src/recipes/dto/*.ts`

Поля `Recipe`:

```ts
userId: ObjectId;
name: string;
nameNormalized: string;
description?: string;
photoUrl?: string;
mealTypes?: Array<'breakfast' | 'lunch' | 'dinner' | 'snack' | 'other'>;
tags?: string[];

servingName?: string; // например "тарелка", "кусок", "порция"
servingGrams?: number;
totalCookedWeightG: number;

calculationMode: 'manual' | 'ingredients' | 'mixed';

ingredients: Array<{
  productId?: ObjectId;
  productName: string;
  grams: number;
  kcalPer100g: number;
  proteinPer100g: number;
  fatPer100g: number;
  carbPer100g: number;
  kcal: number;
  protein: number;
  fat: number;
  carb: number;
}>;

kcalPer100g: number;
proteinPer100g: number;
fatPer100g: number;
carbPer100g: number;

totalKcal: number;
totalProtein: number;
totalFat: number;
totalCarb: number;

linkedProductId?: ObjectId;
isArchived: boolean;
createdAt;
updatedAt;
```

### Расчет КБЖУ

Если `calculationMode = ingredients`:

- суммировать КБЖУ всех ингредиентов;
- итоговое КБЖУ на 100 г считать от `totalCookedWeightG`;
- формула:

```ts
kcalPer100g = totalKcal / totalCookedWeightG * 100
proteinPer100g = totalProtein / totalCookedWeightG * 100
fatPer100g = totalFat / totalCookedWeightG * 100
carbPer100g = totalCarb / totalCookedWeightG * 100
```

Если `manual`:

- ингредиенты опциональны или пустые;
- пользователь вводит КБЖУ на 100 г сам;
- `totalCookedWeightG` все равно желательно хранить, если указана полная порция.

Если `mixed`:

- ингредиенты используются как черновой расчет;
- пользователь может вручную переопределить итоговые КБЖУ на 100 г;
- сохранить флаг `manualOverride: true` или `calculationMode: 'mixed'`.

### API endpoints

Добавить:

```http
GET /recipes
GET /recipes/:id
POST /recipes
PATCH /recipes/:id
DELETE /recipes/:id
POST /recipes/:id/duplicate
POST /recipes/:id/create-entry
```

`GET /recipes` query:

- `search`
- `mealType`
- `tag`
- `limit`
- `offset`
- `includeArchived`

`POST /recipes/:id/create-entry` body:

```ts
{
  date: string;
  time?: string;
  mealType?: MealType;
  grams: number;
}
```

Endpoint должен создать обычную `Entry`, используя рассчитанные КБЖУ блюда.

### Интеграция с Product

Добавить `RECIPE` в:

```ts
export type ProductSource = 'OFF' | 'USER' | 'CUSTOM_SEED' | 'BARCODE' | 'RECIPE';
```

При создании/обновлении рецепта:

- создать или обновить связанный `Product`;
- `Product.name = Recipe.name`;
- `Product.kcalPer100g = Recipe.kcalPer100g`;
- `Product.createdBy = userId`;
- `Product.source = 'RECIPE'`;
- `Product.sourceId = recipe._id`.

В `ProductsService.findAll`:

- блюда должны находиться поиском как продукты;
- вернуть поле `source`;
- frontend должен уметь показывать бейдж "Блюдо".

### Фото блюда

Сделать минимально надежный вариант.

Вариант MVP:

- хранить фото как base64/dataUrl нельзя, если оно большое;
- лучше добавить upload endpoint и сохранять файл в локальную папку в dev, например `apps/api/uploads/recipes`;
- в базе хранить `photoUrl`.

Endpoints:

```http
POST /recipes/:id/photo
DELETE /recipes/:id/photo
```

Требования:

- принимать только image MIME types;
- лимит размера, например 5 MB;
- проверять владельца рецепта;
- отдавать uploads статикой;
- для frontend сделать preview до загрузки.

Если upload пока сложно, сделать временный вариант:

- поле `photoUrl`;
- пользователь может прикрепить URL;
- но UI должен быть подготовлен под file upload позже.

## Frontend

### Новые маршруты

Добавить:

```txt
/recipes
/recipes/new
/recipes/:id
/recipes/:id/edit
```

Можно назвать в UI "Блюда" или "Рецепты". Лучше "Блюда", потому что пользователь будет добавлять их в дневник как готовую позицию.

### Страница списка блюд `/recipes`

Должна быть mobile-first.

Элементы:

- заголовок "Блюда";
- кнопка "Создать блюдо";
- поиск;
- фильтр по типу приема пищи;
- список карточек блюд;
- empty state с CTA.

Карточка блюда:

- фото или fallback illustration;
- название;
- КБЖУ на 100 г;
- бейдж: "ручное", "из ингредиентов", "с коррекцией";
- быстрые действия:
  - добавить в дневник;
  - открыть;
  - редактировать.

### Редактор блюда `/recipes/new` и `/recipes/:id/edit`

Это главный экран. Он должен быть удобным на телефоне.

Структура редактора:

1. **Шапка**
   - назад;
   - название "Новое блюдо" / "Редактировать блюдо";
   - сохранить.

2. **Фото**
   - большая зона upload;
   - preview;
   - кнопки: "Добавить фото", "Заменить", "Удалить";
   - если фото нет, красивый placeholder.

3. **Основное**
   - название блюда;
   - описание;
   - типы приема пищи;
   - теги.

4. **Способ расчета**
   - segmented control:
     - "Вручную";
     - "Из продуктов";
     - "С коррекцией".

5. **КБЖУ вручную**
   - калории на 100 г;
   - белки на 100 г;
   - жиры на 100 г;
   - углеводы на 100 г.

6. **Ингредиенты**
   - поиск по продуктам из текущей базы;
   - добавление продукта;
   - граммы ингредиента;
   - список ингредиентов;
   - редактирование граммов;
   - удаление ингредиента;
   - итоговая сумма КБЖУ ингредиентов.

7. **Выход блюда**
   - итоговый вес после приготовления;
   - подсказка: "Вес готового блюда нужен, чтобы посчитать КБЖУ на 100 г";
   - быстрые кнопки: "равен сумме ингредиентов", "-10%", "-20%".

8. **Итог**
   - карточка рассчитанного КБЖУ на 100 г;
   - пример порции: 100 г / servingGrams;
   - предупреждения валидации.

9. **Сохранение**
   - sticky bottom button "Сохранить блюдо";
   - если редактирование: "Сохранить изменения".

### UX редактора

Требования:

- Все поля должны быть крупными и удобными для пальца.
- Sticky save button внизу.
- Не терять введенные данные при переключении режима расчета.
- При выходе с несохраненными изменениями спрашивать подтверждение.
- Числовые поля должны открывать numeric keyboard.
- Ошибки показывать рядом с полем, не через `alert`.
- После сохранения предложить:
  - "Добавить в дневник";
  - "Остаться в блюде";
  - "К списку блюд".

### Добавление блюда в дневник

В `AddEntryPage`:

- поиск должен находить блюда вместе с продуктами;
- блюдо визуально помечать бейджем "Блюдо";
- если у блюда есть фото, показывать миниатюру;
- после выбора пользователь вводит граммы как обычно;
- entry должна сохраняться через текущий `/entries`.

Опционально добавить быстрый flow:

- на странице блюда кнопка "Добавить в дневник";
- открывает bottom sheet:
  - дата;
  - прием пищи;
  - граммы;
  - preview КБЖУ;
  - сохранить.

### Связь с шаблонами

Не заменять шаблоны блюдами.

Но можно добавить:

- из блюда можно создать шаблон приема пищи только если пользователь явно хочет;
- шаблон может включать блюдо как один item, потому что блюдо является `Product` с `source: 'RECIPE'`.

## UI/Design требования

Стиль должен быть красивым, но не перегруженным.

Рекомендации:

- mobile-first;
- карточки до 8px border-radius, если текущая дизайн-система не требует иначе;
- фото блюда - главный визуальный элемент, но не должно занимать весь экран;
- ингредиенты показывать плотным списком;
- итог КБЖУ закрепить в понятной summary card;
- использовать существующие `Card`, `Button`, `Input`, `Text`, `BottomSheet`, `EmptyState`;
- не делать маркетинговый landing;
- первый экран `/recipes` должен быть рабочим списком.

## Валидация

Backend и frontend должны проверять:

- название обязательно;
- название минимум 2 символа;
- `totalCookedWeightG > 0`;
- КБЖУ не отрицательные;
- граммы ингредиента `> 0`;
- при режиме `ingredients` должен быть хотя бы один ингредиент;
- фото не больше 5 MB;
- фото только `image/jpeg`, `image/png`, `image/webp`;
- пользователь может редактировать только свои блюда.

## Миграции и совместимость

Текущие записи дневника ломать нельзя.

Требования:

- старые `Entry` должны продолжать работать;
- старые `Product` должны продолжать работать;
- если блюдо удалено/архивировано, старые записи в дневнике должны сохранить `productName` и КБЖУ;
- удаление блюда лучше делать soft-delete через `isArchived`;
- связанный `Product` можно скрывать из поиска при archive.
